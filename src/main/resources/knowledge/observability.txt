Observability in Spring AI Fundamentals

Observability measures the running application's behavior. It helps distinguish time spent in HTTP handling, advisors, document retrieval, model inference, and tool execution. Spring AI uses the same Micrometer ObservationRegistry and Spring Boot Actuator stack as the rest of the service. Observation handlers convert instrumented operations into metrics, traces, or selected log events.

Metrics aggregate many operations over time and support dashboards and alerts. Traces describe one request as timed parent and child spans. Advisor durations include downstream operations, so adding all nested timers or span durations double-counts work. A RAG request may show memory and retrieval advisors, a vector query, and a model call. First-use indexing adds chunk loading and embedding operations before normal retrieval. Tools mode can show model, tool, and another model operation.

This app includes Actuator and a Prometheus meter registry. The management server binds to 127.0.0.1:9090 by default, with APP_MANAGEMENT_PORT selecting another port. It exposes health, info, metrics, and prometheus endpoints under /actuator. The learning UI and chat API remain on the application port, normally 8080. Manually constructed vector stores and Ollama HTTP clients use the shared observation registry as well as the auto-configured Spring AI model, tool-execution, and chat-client components.

Relevant operation names include spring.ai.chat.client for ChatClient calls and streams, spring.ai.advisor for advisor work, gen_ai.client.operation for model provider calls, spring.ai.tool for tool execution, and db.vector.client.operation for vector-store add, delete, and query operations. Meters appear only after the corresponding operation runs. A tool metric requires an executed tool; simply selecting tools mode does not cause a tool call.

Low-cardinality attributes have a bounded set of values, such as provider, operation, and registered tool name. They can go on metrics and traces. Per-request values such as conversation IDs belong in high-cardinality trace detail rather than metric labels. Each distinct metric-label combination creates a separate time series. Token counts are numeric measurements, not values to turn into new label dimensions. This app omits raw vector-query text and filter expressions from vector-store span attributes.

Spring AI 2.0.1 records model token counters under gen_ai.client.token.usage with the tag gen_ai.token.type. It emits input, output, and total series when the corresponding provider usage fields are available. Input includes supplied prompts, history, and retrieved context; output is generated completion text. Use total, or add input and output, but do not add all three. Provider support determines which chat, embedding, and streaming usage values are available. A failure before receiving usage can have timing telemetry without token counts.

Token usage is a workload signal and can support cost estimation for a paid model, but it is not a bill. This app uses local Ollama inference without per-token invoices. Paid-provider estimates need model-specific prices and any separate cached-token or other usage rates. Prometheus normalizes dotted metric names and label names; the token counter is exposed as gen_ai_client_token_usage_total with a gen_ai_token_type label. Actuator metrics use the original dotted Micrometer names.

OTLP trace export is disabled by default, so ordinary app startup does not require a collector. Local tracing context, log correlation IDs, and HTTP propagation remain active. The tracing Spring profile enables management.tracing.export.otlp.enabled and configures management.opentelemetry.tracing.export.otlp.endpoint using OTEL_EXPORTER_OTLP_TRACES_ENDPOINT with a default of http://localhost:4318/v1/traces. The general tracing switch stays enabled so propagation works even while OTLP transport is disabled. In that profile TRACING_SAMPLING_PROBABILITY defaults to 1.0 for the local exercise; the ordinary configuration samples 0.1. Metrics are independent of trace sampling. OTLP metric and log push exporters stay disabled, while Prometheus exposes metrics. A collector and compatible trace-viewing backend must run separately; the app does not start them.

The instrumented Ollama HTTP clients propagate W3C traceparent context to downstream HTTP services. An incoming traceparent header can connect the request to an existing trace. A downstream gateway or inference server must also record and export compatible telemetry for its own operations to appear. Header propagation alone does not make Ollama produce a trace UI. Active trace and span IDs can correlate log entries with a request.

Spring AI observation content logging is opt-in. The defaults leave spring.ai.chat.client.observations.log-prompt and log-completion false, as well as spring.ai.chat.observations.log-prompt, log-completion, and include-error-logging. The client prefix records the application-facing request before advisor enrichment; the model prefix sees the provider-facing prompt after memory, retrieval, and formatting instructions. Comparing the two can explain how the advisor chain changed context.

The separate spring.ai.tools.observations.include-content flag controls tool argument and result content, and spring.ai.vectorstore.observations.log-query-response controls retrieved query documents. They are false by default. The ai-content-debug Spring profile enables the content flags for a deliberate local debugging session; it can be combined with tracing using SPRING_PROFILES_ACTIVE=tracing,ai-content-debug. Enabling content can expose private messages, documents, tool data, or error details in logs or spans. Tool names, descriptions, and schemas remain metadata even when argument/result content is excluded. Trace correlation does not remove content sensitivity.

To inspect the application, send a chat question and let its event stream finish, then query /actuator/metrics or /actuator/prometheus on the management server. Missing meters can mean an operation has not run. Missing traces can mean export is disabled, a request was not sampled, or the collector/backend is unavailable. Missing token counters can mean the provider did not return usage. Latency and aggregate-usage investigations do not require enabling prompt logging.
