Model Context Protocol in Spring AI Fundamentals

Model Context Protocol, or MCP, standardizes how an AI application discovers and uses capabilities supplied by another program. Without a shared protocol, each host needs a separate custom integration for every service. A reusable MCP server can expose the same capability interface to several compatible hosts. MCP standardizes capability exchange; it does not decide how a host builds prompts, uses a model, manages memory, or selects context.

The MCP host is the AI application that manages the conversation and decides which capabilities reach its model. It creates an MCP client for each configured server connection. The server is a program that publishes capabilities and controls their execution. A server can run locally or remotely and does not need to use a language model. In this project, the browser and chat application are the host, Spring AI manages its client, and another instance of the same application acts as the MCP server.

MCP uses JSON-RPC 2.0. A request contains a method name, parameters, and an ID; its response uses the same ID. A notification does not expect a response. The protocol revision implemented by this project's dependencies initializes a connection and negotiates its version and capabilities. The client discovers tool names, descriptions, and schemas using tools/list. The host passes only selected schemas to its model. When the model requests a tool, the client sends tools/call to the server. The server validates arguments, executes application code, and returns a result that feeds the next model request. The model produces the user-facing answer, while application code actually performs tool execution.

Stdio and Streamable HTTP are different MCP transports. Stdio connects a host to a launched local process using standard input and output; stdout is reserved for protocol messages, and diagnostic logs belong on stderr. Streamable HTTP connects clients to an independently running HTTP server and can stream responses using Server-Sent Events. It replaces the older dedicated HTTP+SSE transport, which is deprecated in Spring AI. This project uses Streamable HTTP at /mcp and does not launch stdio commands or download external server packages.

MCP servers publish tools, resources, and prompts. Tools are operations whose schemas can be offered to the model under the host's control. Resources supply context selected by an application, often using a URI or URI template. Prompts supply reusable message templates selected by a user or host. Listing a resource or prompt does not automatically add it to a conversation, and publishing it does not automatically turn it into a model tool. Other optional protocol features include argument completions, logging, progress, and list-change notifications.

The learning MCP server publishes two tools. learning_outline accepts topic and returns a public lesson outline. learning_server_time accepts no arguments and returns the current time in the MCP server's configured timezone. The server also publishes the resource template learning://topics/{topic}, which returns the same outline as text/plain, and the prompt study_topic, which accepts topic and returns a user message requesting an explanation, Java example, and practice question. Accepted topics are fundamentals, spring-ai, advisors, rag, tools, and mcp. Unknown topics fail server-side validation. APP_TIME_ZONE selects the server-owned timezone; the model cannot supply it.

Spring AI's spring-ai-starter-mcp-server-webflux starter configures the reactive server. The mcp-server Spring profile enables spring.ai.mcp.server.enabled, selects spring.ai.mcp.server.type=ASYNC and spring.ai.mcp.server.protocol=STREAMABLE, and exposes /mcp. The annotated LearningMcpCapabilities component is active only in that profile. @McpTool marks tools, @McpToolParam describes tool arguments and their required status, @McpResource declares a resource URI template, and @McpPrompt marks a reusable prompt. @McpArg describes a prompt argument. The server's annotated handlers return Mono to match ASYNC type; synchronous annotated handlers would be ignored by the ASYNC scanner.

@Tool and @McpTool serve different boundaries. @Tool supplies a method for local application tool calling, while @McpTool publishes a capability over MCP to other applications. Spring can also convert ToolCallback or ToolCallbackProvider beans into MCP server tools. This project disables that conversion with spring.ai.mcp.server.tool-callback-converter=false, so local tools and discovered remote callbacks are not implicitly republished. It exposes only the explicitly annotated server capabilities. Read-only tool annotations are descriptive hints, not enforcement; Java implementation and access controls determine what is allowed.

Run the server with SPRING_PROFILES_ACTIVE=mcp-server mvn spring-boot:run. It binds to 127.0.0.1:8090 by default and puts management endpoints on 127.0.0.1:9091. MCP_SERVER_PORT and MCP_MANAGEMENT_PORT change those ports. Although the shared application includes model beans, serving the public catalogue requires no running Ollama service or model inference.

The host uses spring-ai-starter-mcp-client-webflux. The mcp-client Spring profile enables an ASYNC client named spring-ai-learning-host with a 30s request timeout and one named Streamable HTTP connection, lessons. Its server URL defaults to http://127.0.0.1:8090 and can be changed with MCP_SERVER_URL. The URL is the server origin and the endpoint is /mcp. Spring AI manages connection initialization, cleanup, discovery, and adaptation of remote tools into Spring AI tool callbacks. All MCP clients in one application use the same SYNC or ASYNC type; mixing types is not supported.

Start the server first because the mcp-client profile connects during application startup. With Ollama running and a tool-capable model installed, run SPRING_PROFILES_ACTIVE=mcp-client OLLAMA_CHAT_MODEL=llama3.1:latest mvn spring-boot:run in a second terminal. Open the normal application on port 8080, select Use MCP tools, and ask the server for a lesson outline or its current time. Install the model explicitly with ollama pull llama3.1:latest; the application does not download models automatically. The default llama3:latest is intended for tutor and RAG modes rather than tool execution.

RAG remains the browser and API default. Both MCP client and server are disabled during ordinary startup, so ordinary startup makes no MCP connection. MCP mode is an explicit alternative to rag, tutor, and local tools. It does not retrieve notes or register local LearningTools. McpRemoteTools limits remote model-visible tools to learning_outline and learning_server_time. Only MCP chat requests receive those callbacks; they are not installed as global ChatClient tools. The browser does not automatically read MCP resources or use MCP prompts. The MCP notes themselves are bundled RAG documents grouped under the tools metadata topic; the API's RAG topic choices remain all, rag, spring-ai, and tools.

GET /api/mcp reports enabled and the tools array. With the client disabled it returns enabled=false and an empty list without a remote connection. An enabled integration that cannot supply tools reports a safe 503 setup error. POST /api/chat with mode=mcp requests remote tools; no topic field should be supplied because the chat topic selector is for RAG only. An unavailable MCP integration reports a setup problem instead of switching to another chat mode. Bounded session memory is separate for all four modes, and starting a new chat clears their histories.

Spring AI also provides optional client annotations for server-initiated interactions. @McpSampling can handle a server request for host-managed model sampling, @McpElicitation can handle a request for user input, @McpLogging receives logs, @McpProgress receives progress, and @McpToolListChanged, @McpResourceListChanged, and @McpPromptListChanged handle offering changes where the protocol supports them. The clients attribute scopes a handler to named connections, and reactive handlers must match an ASYNC client. A host must apply its own access policies and budgets to sampling and honor a user's refusal of elicitation. This demo does not register sampling or elicitation handlers or implement a dynamic model-tool refresh workflow. Availability and deprecation of callbacks depend on the protocol revision.

Authorization is a separate boundary from discovery. The HTTP MCP endpoint does not gain authentication simply because it uses an MCP starter. MCP authorization guidance builds on OAuth and protected-resource metadata discovery. A client obtains a token intended for a particular resource; the server validates credentials, audience, scopes, and operation permissions. Do not forward an incoming MCP access token to downstream APIs; obtain a separate token scoped to the downstream service. Elicitation asks for information or consent and does not replace authorization. Roots are cooperative scope information and do not enforce a filesystem sandbox. Treat tool arguments, descriptions, and results as untrusted data and expose only intended capabilities.

This demo has no OAuth login or token validation and serves public read-only learning material. The server binds to loopback and checks Host and browser Origin to limit local exposure. These checks do not authenticate callers. A protected HTTP deployment needs a security layer compatible with the application's WebFlux stack, including authorization for individual operations. Experimental security libraries have version and framework restrictions; a WebMVC-only example is not automatically applicable to a reactive WebFlux server.

MCP protocol revisions are date strings. This project's Spring AI 2.0.1 dependencies resolve MCP Java SDK 2.0.0. Its supported handshake-based revisions extend through 2025-11-25, and the SDK integration tests verify that client and server negotiate 2025-11-25. The newer 2026-07-28 specification describes per-request version and capability metadata and server/discover, which a client may call before other requests. Those newer semantics and changes to older feature lifecycles are not automatically implemented by the project's older protocol support. Selecting Spring's STATELESS server deployment mode is not the same as enabling the 2026-07-28 protocol revision. Check the resolved SDK and revision-specific primary documentation before adopting a feature from a tutorial.

MCP tests use the real Java SDK against a local Streamable HTTP server to verify initialization, discovery, tool schemas and invocation, resource reading, prompt retrieval, and invalid-topic handling. A controlled mocked model requests a remote tool; the real HTTP tool result is then passed into the next model prompt. These deterministic integration checks do not require live Ollama, external services, or generated prose matching an exact string. Testing transport and application wiring is separate from judging whether a real model chooses and explains a tool result well.

Primary references are the official MCP architecture and versioning pages and the Spring AI MCP client and server starter references. Read the protocol revision and framework version alongside their examples.
