Testing AI applications

Separate deterministic application behavior from probabilistic model output. Use JUnit and Mockito with a stubbed or mocked ChatModel to test prompt construction, advisor wiring, tool validation and execution, SearchRequest settings, structured-output mapping, and error handling. Exact-string assertions are appropriate for fixed mock responses; assess useful properties instead of exact wording for live model answers. Most tests should be fast, repeatable, and independent of Ollama. Join all streaming chunks before checking an application's final source list, rather than inspecting only the first chunk.

The Spring AI Evaluator contract exposes evaluate(EvaluationRequest) and returns an EvaluationResponse. The three request inputs are userText (the user's question), dataList (supporting content, such as a List<Document> used as evidence), and responseContent (the generated answer). EvaluationResponse.isPass() reports the judge's verdict. For retrieval-augmented generation, evaluate with the same retrieved documents that were supplied to the answer model.

RelevancyEvaluator asks a judging ChatClient whether the answer addresses the question in line with its supplied context. FactCheckingEvaluator checks whether the response claim is supported by the evidence. Relevance and factual support are distinct qualities; an answer can be on topic while making an unsupported claim. These evaluators call a real judge model, so their results are probabilistic rather than deterministic.

A custom RelevancyEvaluator PromptTemplate is configured with RelevancyEvaluator.builder().chatClientBuilder(judgeBuilder).promptTemplate(template).build(). The template must retain {query}, {response}, and {context}; they receive the question, answer, and evidence. Write an explicit rubric and request a single YES or NO without explanation. In Spring AI 2.0.1, both evaluators strip surrounding whitespace and pass only an exact case-insensitive yes; any other judge output fails. FactCheckingEvaluator's custom evaluationPrompt uses {document} and {claim} instead of the relevancy placeholders.

Capture evaluation evidence from the same advisor response as the generated answer, not from a second similarity search. This app uses QuestionAnswerAdvisor.RETRIEVED_DOCUMENTS from ChatClientResponse.context(). Its ChatService.answerWithContext(question, conversationId, topic) helper aggregates the existing streaming RAG path into a RagAnswer containing question, answer, and retrievedDocuments. The answer excludes the browser's appended source list, while the retrieved documents are the ones used for generation. A modular RetrievalAugmentationAdvisor example instead uses chatResponse.getMetadata().get(RetrievalAugmentationAdvisor.DOCUMENT_CONTEXT); choose the key matching your actual advisor.

An evaluation test should check useful properties such as relevance, grounding, required information, and unsupported claims rather than exact wording. Use stable prompts and judge settings, including a low temperature when the provider supports it. Include positive and negative examples, and treat a verdict as evidence rather than proof. The judge may disagree with itself or with a human reviewer.

Integration tests can run real models and vector stores in disposable Testcontainers infrastructure. The spring-ai-spring-boot-testcontainers integration and Spring Boot service connections can provide connection details for supported containers. Match the module, container implementation, and service-connection support to the Spring AI and Spring Boot versions in use. These tests are slower and need Docker and model resources, so run them in a dedicated integration or release tier rather than on every edit.

This learning app's regular Maven suite focuses on the deterministic shell: ChatModel and VectorStore are mocked while tests verify prompt grounding, retrieval settings, advisor behavior, tools, and API responses. Running mvn test does not start Ollama or require Docker. The opt-in command mvn -Pai-evaluation verify runs real-model answer evaluations using Ollama for the answer, embeddings, and judge. OLLAMA_JUDGE_MODEL selects the judging model and defaults to llama3.1:latest. Install the configured models first; failed judge calls or verdicts should be investigated rather than silently skipped. Testcontainers remains educational, and this profile does not start containers.
